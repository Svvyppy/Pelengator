# План перехода Peleng на C++20 coroutines

## 1. Цель миграции

Цель перехода не в том, чтобы заменить прерывания STM32 или сделать DSP
параллельным. Корутины должны заменить ручной опрос состояний и сделать
асинхронные сценарии последовательными и читаемыми.

Текущая схема:

```text
DMA IRQ
  -> HAL callback
  -> очередь готовых блоков
  -> опрос из while (1)
  -> Peleng::Process()
  -> DSP
  -> очередь UART
  -> UartTelemetryProcess()
```

Целевая схема:

```text
DMA IRQ
  -> публикация события
  -> очередь scheduler
  -> возобновление coroutine в main
  -> DSP
  -> публикация результата
  -> coroutine телеметрии
  -> ожидание завершения UART IRQ
```

Основные ограничения проекта:

- STM32G473, Cortex-M4, bare metal, без RTOS;
- C++20 и `arm-none-eabi-g++`;
- исключения и RTTI отключены;
- DMA работает в circular mode;
- один блок из 1024 отсчётов должен быть обработан быстрее `4.096 ms`;
- ISR должны оставаться короткими;
- количество задач и событий известно заранее;
- динамическая память в рабочем цикле нежелательна.

## 2. Основные правила архитектуры

### 2.1. Не выполнять DSP внутри ISR

HAL callback не должен непосредственно вызывать `resume()` у coroutine, которая
запускает `ProcessHalfTransfer()`. Иначе код после `co_await` продолжит работу в
контексте прерывания.

ISR должен:

1. Зафиксировать аппаратное событие.
2. Положить `coroutine_handle` в очередь готовых задач.
3. Завершиться.

Возобновляет coroutine только scheduler, вызванный из `main`.

### 2.2. Корутина не заменяет очередь событий

Пока обрабатывается один DMA-блок, может стать готов следующий. Единственный
флаг `block_ready` потеряет события. Очередь `SignalBlock` должна сохраниться,
даже когда её потребителем станет coroutine.

### 2.3. Не приостанавливать обработку одного DSP-блока

Обработка четырёх каналов и расчёт задержек остаются синхронной операцией:

```text
получить готовый блок
  -> обработать все четыре канала
  -> вычислить задержки
  -> опубликовать результат
```

Между каналами не должно быть `co_await`: соответствующая половина DMA-буфера
будет повторно использована аппаратурой.

### 2.4. Владение coroutine frame должно быть явным

Для каждой coroutine необходимо понимать:

- кто владеет её `std::coroutine_handle`;
- кто и когда вызывает `resume()`;
- кто и когда вызывает `destroy()`;
- может ли владелец быть уничтожен, пока coroutine ожидает событие;
- где размещён coroutine frame.

## 4. Этап 1: минимальный тип `Task`

Начать следует с независимой от HAL части в `src/async/Task.h`.

### Что нужно изучить

- преобразование coroutine-функции компилятором;
- назначение `promise_type`;
- `std::coroutine_handle`;
- `initial_suspend()` и `final_suspend()`;
- `co_return`;
- время жизни локальных переменных coroutine;
- различие eager и lazy coroutine.

### Первый интерфейс

На первом шаге достаточно поддержать только `Task<void>`:

```cpp
namespace async {

class Task
{
public:
    struct promise_type;

    Task(Task&& other) noexcept;
    Task& operator=(Task&& other) noexcept;

    Task(const Task&) = delete;
    Task& operator=(const Task&) = delete;

    ~Task();

    bool Done() const;
    void Resume();

private:
    explicit Task(std::coroutine_handle<promise_type> handle);

    std::coroutine_handle<promise_type> handle_{};
};

} // namespace async
```

Это ориентир для упражнения, а не обязательная окончательная форма API.

### Решения, которые нужно принять самостоятельно

1. Запускается ли задача сразу или при первом `Resume()`?
2. Что возвращает `initial_suspend()`?
3. Что возвращает `final_suspend()`?
4. Может ли `Resume()` вызываться для завершённой задачи?
5. Уничтожает ли деструктор незавершённую coroutine?
6. Как обрабатывать `unhandled_exception()` при `-fno-exceptions`?

Для первого варианта удобна lazy coroutine:

- `initial_suspend()` приостанавливает выполнение;
- владелец явно запускает задачу;
- `final_suspend()` оставляет frame доступным для уничтожения владельцем.

### Учебная coroutine

```cpp
async::Task Example()
{
    // Записать контрольную отметку.
    co_return;
}
```

Затем добавить собственный awaitable, который один раз приостанавливает задачу.

### Критерий завершения

- задача создаётся, запускается и завершается;
- move не приводит к двойному `destroy()`;
- копирование запрещено;
- frame уничтожается ровно один раз;
- `Resume()` не вызывается для пустого или завершённого handle.

## 5. Этап 2: понять протокол awaitable

До реализации scheduler полезно написать простой учебный awaitable:

```cpp
struct SuspendOnce
{
    bool await_ready() const noexcept;
    void await_suspend(std::coroutine_handle<> handle) noexcept;
    void await_resume() const noexcept;
};
```

### Что проверить

1. Если `await_ready()` возвращает `true`, coroutine не приостанавливается.
2. Если он возвращает `false`, вызывается `await_suspend()`.
3. Код после `co_await` выполняется только после `resume()`.
4. Локальные переменные сохраняют значения между приостановками.
5. `await_resume()` может вернуть результат операции.

### Практическое упражнение

Сохранить handle в `SuspendOnce`, затем возобновить его вручную из теста.
На этом этапе не использовать IRQ и глобальный scheduler.

## 6. Этап 3: однопоточный scheduler

Scheduler нужен, чтобы ISR не выполнял прикладной код.

### Предлагаемый интерфейс

```cpp
namespace async {

bool Schedule(std::coroutine_handle<> handle);
void RunReady();
bool HasReadyWork();

} // namespace async
```

### Внутреннее устройство

Использовать кольцевую очередь фиксированного размера:

```text
array<coroutine_handle<>, N>
head
count
overflow_count
```

На первом варианте достаточно одного producer-контекста ISR и одного
consumer-контекста `main`, но доступ всё равно должен быть защищён.

### Правила

- `Schedule()` не вызывает `resume()`;
- `RunReady()` извлекает handles и вызывает `resume()` в `main`;
- пустой handle не добавляется;
- завершённый handle не должен планироваться;
- переполнение очереди считается и доступно в диагностике;
- critical section должна быть минимальной;
- `resume()` нельзя выполнять с отключёнными прерываниями.

### Интеграция без удаления старого кода

```cpp
while (true) {
    async::RunReady();
    UartTelemetryProcess();
    (void)g_peleng.Process();
}
```

На этом этапе scheduler ещё не управляет Peleng или UART.

### Критерий завершения

- несколько задач выполняются в порядке постановки;
- постановка задачи не запускает её немедленно;
- очередь корректно обрабатывает переход индексов через конец массива;
- переполнение не повреждает очередь;
- scheduler ничего не делает при пустой очереди.

## 7. Этап 4: событие, ожидаемое через `co_await`

Следующий примитив связывает источник события и ожидающую coroutine.

### Начальный вариант

Для обучения реализовать событие с одним ожидающим:

```cpp
template<typename T>
class Event;
```

Предполагаемые операции:

```cpp
auto operator co_await();
bool NotifyFromIsr(T value);
bool HasPendingValue() const;
```

### Семантика

Если значение уже опубликовано, `co_await` возвращает его без приостановки.
Если значения нет, awaitable регистрирует handle текущей coroutine.

`NotifyFromIsr()`:

1. Сохраняет значение.
2. Забирает зарегистрированный handle.
3. Передаёт handle в `async::Schedule()`.
4. Не вызывает `resume()`.

### Главная гонка

Нужно явно разобрать последовательность:

```text
await_ready() проверил: значения нет
IRQ опубликовал значение
await_suspend() зарегистрировал ожидающий handle
```

Если проверка и регистрация не согласованы, событие будет потеряно.

Возможные решения:

- critical section вокруг повторной проверки и регистрации;
- `await_suspend()` возвращает `bool` и отменяет приостановку, если событие
  появилось между проверками;
- единая атомарная модель состояния.

Для Cortex-M4 и текущего bare-metal проекта короткая critical section будет
проще для первого варианта.

### Ограничение первого варианта

Поддержать только одного ожидающего. Попытка зарегистрировать второго должна
обнаруживаться через assert, статус ошибки или диагностический счётчик.

### Host-тесты

- уведомление после начала ожидания;
- уведомление до начала ожидания;
- повторное уведомление;
- повторное ожидание после получения значения;
- отсутствие двойного планирования;
- доставка значения через `await_resume()`.

## 8. Этап 5: первая аппаратная coroutine на UART

UART является более удобной первой интеграцией, чем ADC/DSP: ошибка не нарушит
временной бюджет обработки входного сигнала.

### Шаг 5.1. Получать настоящее событие завершения

Добавить обработку:

```cpp
extern "C" void HAL_UART_TxCpltCallback(UART_HandleTypeDef* huart);
```

Callback должен:

1. Проверить нужный UART.
2. Зафиксировать завершение передачи.
3. Запланировать ожидающую coroutine.
4. Завершиться.

Опрос `huart->gState` не должен быть основным сигналом завершения в новой
архитектуре.

### Шаг 5.2. Реализовать awaitable одной передачи

Целевой вид вызова:

```cpp
const auto status = co_await UartTransmit{huart, data, size};
```

Awaitable должен:

1. Проверить аргументы.
2. Переключить RS-485 в TX.
3. Вызвать `HAL_UART_Transmit_IT`.
4. При `HAL_OK` приостановить coroutine до callback.
5. При ошибке не ждать несуществующее IRQ.
6. После возобновления переключить RS-485 в RX.
7. Вернуть результат операции.

### Важный вопрос времени жизни

Передаваемый буфер должен существовать до завершения IRQ. Нельзя передавать
указатель на локальный массив обычной функции, завершившейся до callback.

Безопасные варианты:

- сообщение хранится в существующем слоте UART-очереди;
- данные являются частью coroutine frame;
- буфер принадлежит долгоживущему объекту.

Для текущего проекта проще оставить сообщения в существующей кольцевой очереди.

### Шаг 5.3. Реализовать `TelemetryWorker`

```cpp
async::Task TelemetryWorker()
{
    while (true) {
        auto message = co_await NextTelemetryMessage();
        co_await UartTransmit(message);
    }
}
```

Функции сериализации задержек пока не менять. Они по-прежнему формируют
сообщение и кладут его в очередь.

### Шаг 5.4. Удалить UART polling

Только после проверки на плате удалить:

- вызовы `UartTelemetryProcess()` из `main`;
- проверку готовности UART как state machine;
- ручной флаг `tx_active`, если он больше не нужен.

### Критерий завершения

- сообщения передаются строго последовательно;
- RS-485 возвращается в RX после завершения;
- буфер не переиспользуется во время передачи;
- ошибка запуска UART не блокирует worker навсегда;
- заполненная очередь имеет определённую политику: drop newest, drop oldest или
  backpressure;
- UART callback не выполняет форматирование и не вызывает `resume()`.

## 9. Этап 6: ожидание готового ADC-блока

Существующая очередь `SignalBlock` должна стать источником данных для awaitable.

### Целевой интерфейс

```cpp
async::Task<platform::SignalBlock> NextSignalBlock();
```

Если обобщённый `Task<T>` пока слишком сложен, можно начать с отдельного
awaitable:

```cpp
const platform::SignalBlock block =
    co_await platform::ReadySignalBlock{};
```

Второй вариант проще и позволяет отложить реализацию композиции `Task<T>`.

### Алгоритм awaitable

1. Проверить очередь готовых блоков.
2. Если блок есть, забрать его без приостановки.
3. Если очередь пуста, зарегистрировать handle.
4. Повторно проверить состояние под защитой от IRQ.
5. При появлении блока приостановку отменить.
6. После IRQ scheduler возобновляет coroutine.
7. `await_resume()` извлекает следующий блок.

### Изменение ADC callbacks

Callbacks по-прежнему:

- считают завершения по всем четырём ADC;
- публикуют `FirstHalf` или `SecondHalf`;
- учитывают переполнение очереди.

Дополнительно после публикации блока callback должен разбудить ожидающего через
scheduler.

### Что нельзя делать

- хранить только последнюю половину вместо очереди;
- запускать DSP из HAL callback;
- разрешить двум coroutines одновременно потреблять одну ADC-очередь;
- держать IRQ выключенными во время DSP;
- очищать очередь при каждом новом ожидании.

### Критерий завершения

- порядок `FirstHalf`, `SecondHalf` сохраняется;
- события не теряются между `await_ready()` и `await_suspend()`;
- переполнение диагностируется;
- DSP выполняется в thread mode, а не handler mode;
- существующие debug counters продолжают работать.

## 10. Этап 7: преобразование `Peleng::Process()` в coroutine

После появления ожидания ADC-блока можно заменить polling-интерфейс.

### Текущая ответственность

`Peleng::Process()`:

1. Проверяет очередь готовых блоков.
2. Вычисляет offset половины DMA-буфера.
3. Обрабатывает блок.
4. Публикует последние задержки.

### Целевая форма

```cpp
async::Task Peleng::Run()
{
    while (true) {
        const auto block = co_await platform::ReadySignalBlock{};

        const std::size_t offset =
            block == platform::SignalBlock::FirstHalf
                ? 0U
                : SIGNAL_BLOCK_SIZE;

        ProcessHalfTransfer(offset);
        PublishDelays();
    }
}
```

### Порядок изменений

1. Добавить `Run()`, не удаляя `Process()`.
2. Запускать только один из двух путей через compile-time флаг или отдельную
   ветку.
3. Сравнить результаты и временные характеристики.
4. Проверить контекст выполнения через `__get_IPSR() == 0`.
5. После проверки удалить `Process()`.

### Критерий завершения

- одна coroutine Peleng постоянно ожидает новые блоки;
- на каждый извлечённый блок вызывается ровно одна обработка;
- время DSP не ухудшилось существенно;
- coroutine не накапливает frames на каждой итерации;
- в steady state нет новых выделений памяти.

## 11. Этап 8: публикация результатов DSP

Сейчас результат передаётся через:

```cpp
TryGetLatestDelays()
```

Есть два возможных направления.

### Вариант A: очередь результатов

Peleng помещает `DelayMeasurements` в фиксированную очередь, а telemetry
coroutine ждёт следующий результат.

Плюсы:

- каждый результат может быть обработан;
- понятное разделение producer/consumer.

Минусы:

- нужна дополнительная очередь;
- при медленном UART нужно определить политику переполнения.

### Вариант B: latest value

Peleng заменяет последнее значение и уведомляет потребителя.

Плюсы:

- соответствует текущему `TryGetLatestDelays()`;
- телеметрия может пропускать промежуточные измерения;
- минимальное потребление памяти.

Минусы:

- промежуточные результаты намеренно теряются.

Для текущей телеметрии с отправкой каждого шестнадцатого кадра разумно начать с
latest-value модели и сохранить decimation.

### Критерий завершения

- политика потери результатов сформулирована явно;
- consumer не читает частично записанную структуру;
- публикация результата не выполняет UART-операции;
- decimator имеет то же поведение, что до миграции.

## 12. Этап 9: верхнеуровневая application coroutine

После перевода Peleng и UART сценарий приложения можно описать отдельно от
`main`.

Пример целевого уровня:

```cpp
async::Task Application()
{
    g_peleng.Init();

    uint32_t decimator = 0U;

    while (true) {
        const auto delays = co_await NextDelayMeasurement();

        if ((++decimator % kDelayTxEveryNFrames) == 0U) {
            QueueDelayTelemetry(delays);
        }
    }
}
```

`Application()` необязательно должна сама ждать UART. Если сообщения уже
буферизуются, лучше сохранить отдельный `TelemetryWorker`.

### Целевой `main`

```cpp
int main()
{
    InitHw();

    auto peleng_task = g_peleng.Run();
    auto telemetry_task = TelemetryWorker();
    auto application_task = Application();

    async::Start(peleng_task);
    async::Start(telemetry_task);
    async::Start(application_task);

    while (true) {
        async::RunReady();
    }
}
```

Конкретный API запуска зависит от выбранной модели владения `Task`.

### Критерий завершения

- `main` не содержит прикладной state machine;
- долгоживущие `Task` не уничтожаются раньше времени;
- scheduler остаётся единственным местом вызова `resume()`;
- idle loop не мешает обработке IRQ.

## 13. Этап 10: idle и `__WFI()`

Добавлять сон следует после стабилизации scheduler.

Простой вариант:

```cpp
while (true) {
    async::RunReady();

    if (!async::HasReadyWork()) {
        __WFI();
    }
}
```

### Возможная гонка

IRQ может поставить задачу между проверкой `HasReadyWork()` и `__WFI()`.
Необходимо проверить семантику Cortex-M и выбранную последовательность
инструкций. Для надёжной реализации обычно требуется согласовать проверку
очереди, маскирование IRQ и вход в сон.

На первом рабочем варианте допустимо оставить busy loop. Энергосбережение не
должно внедряться одновременно с основной coroutine-миграцией.

## 14. Этап 11: управление памятью

Компилятор обычно размещает coroutine frame через `operator new`, если не смог
устранить allocation. Для firmware это нужно измерить, а не предполагать.

### Сначала добавить диагностику

Зафиксировать:

- число созданных frames;
- число уничтоженных frames;
- максимальный размер frame;
- использование heap;
- использование stack;
- изменения `.text`, `.data`, `.bss`.

### Затем выбрать стратегию

Возможные варианты:

1. Статические долгоживущие задачи и стандартное выделение только на старте.
2. Собственный фиксированный allocator для `promise_type::operator new`.
3. Общий pool блоков фиксированного размера.
4. Несколько pools для frames разных размеров.

Для проекта с небольшим известным количеством постоянных задач подходит
фиксированный pool либо выделение только во время инициализации с запретом
создания задач в steady state.

### Обязательные ошибки

Нужно определить поведение при:

- нехватке памяти;
- слишком большом frame;
- двойном уничтожении;
- уничтожении ожидающей задачи;
- событии, которое хранит handle уже уничтоженной coroutine.

### Критерий завершения

- после инициализации число allocations не растёт;
- нет висячих handles;
- каждое создание frame соответствует одному уничтожению;
- ошибка allocation обрабатывается определённым способом;
- размер RAM остаётся допустимым.

## 15. Этап 12: `Task<T>` и композиция задач

Не следует начинать миграцию с универсальной coroutine-библиотеки. `Task<T>`
нужен только тогда, когда появится реальная необходимость писать:

```cpp
const auto value = co_await SomeTask();
```

Для композиции задач потребуется:

- хранить continuation вызывающей coroutine;
- вернуть continuation из `final_suspend()`;
- передать результат через `promise_type`;
- корректно поддержать void и non-void задачи;
- определить владение дочерним frame;
- обработать уничтожение родительской задачи.

До этого момента отдельные awaitables для ADC, UART и событий проще и полезнее
для изучения механики.

## 17. Диагностика

Полезно добавить единый snapshot async-подсистемы:

```cpp
struct AsyncDebug
{
    uint32_t scheduled;
    uint32_t resumed;
    uint32_t completed;
    uint32_t scheduler_overflows;
    uint32_t invalid_handles;
    uint32_t frames_created;
    uint32_t frames_destroyed;
    uint32_t adc_events;

```

Также полезны проверки:

```cpp
assert(__get_IPSR() == 0U); // перед тяжёлой обработкой
assert(handle);
assert(!handle.done());     // перед resume
```

Если стандартный `assert` непригоден, использовать локальный debug macro,
который вызывает `Error_Handler()` или записывает причину ошибки.

## 18. Типичные ошибки

### Вызов `resume()` из IRQ

Код после `co_await` неожиданно выполняется внутри ISR. Это увеличивает latency
и может запустить DSP в прерывании.

### Потерянное событие

Событие приходит между `await_ready()` и регистрацией handle.

### Висячий handle

`Task` уничтожена, но `Event` или драйвер всё ещё хранит её handle.

### Двойной `destroy()`

Два объекта `Task` владеют одним frame после некорректного move.

### Resume завершённой coroutine

Завершённый handle повторно попал в scheduler queue.

### Буфер UART уничтожен слишком рано

HAL продолжает читать память после выхода из функции или переиспользования
слота очереди.

### Неограниченное создание задач

Coroutine создаётся на каждой итерации и постепенно расходует heap.

### Корутина воспринимается как поток

Coroutine не выполняется параллельно сама по себе. Она продолжает работу только
когда кто-то вызывает `resume()`.

### Слишком ранняя универсализация

Попытка сразу реализовать cancellation, generic executor, `when_all`,
`Task<T>`, timers и несколько waiters усложнит поиск основных ошибок.

## 21. Контрольные точки обучения

### После `Task`

Нужно уметь своими словами объяснить:

- что хранится в coroutine frame;
- когда выполняется тело coroutine;
- зачем нужен `promise_type`;
- почему handle нельзя бездумно копировать;
- кто уничтожает frame.

### После scheduler

Нужно понимать:

- почему `resume()` определяет контекст выполнения;
- почему ISR только планирует работу;
- как обрабатывается переполнение;
- почему `resume()` выполняется вне critical section.

### После `Event`

Нужно понимать:

- протокол `await_ready/await_suspend/await_resume`;
- где возникает гонка потерянного уведомления;
- как значение передаётся ожидающей coroutine;
- почему нельзя хранить handle после уничтожения задачи.

### После UART

Нужно понимать:

- время жизни асинхронного буфера;
- связь запуска операции и IRQ завершения;
- обработку синхронной ошибки старта;
- отличие очереди сообщений от ожидания одной операции.

### После ADC/Peleng

Нужно понимать:

- почему DMA-очередь остаётся нужна;
- почему DSP не следует дробить suspension points;
- почему coroutine не является отдельным потоком;
- как сохранить real-time deadline при смене orchestration.

## 22. Финальные критерии миграции

Переезд можно считать завершённым, когда:

- `main` выполняет scheduler и idle-логику;
- UART progression больше не опрашивается вручную;
- Peleng ожидает DMA-блок через `co_await`;
- ISR только публикуют события и планируют handles;
- DSP всегда выполняется вне ISR;
- события ADC не теряются;
- UART-буферы живут до завершения передачи;
- frame ownership определён для каждой coroutine;
- в steady state отсутствуют allocations;
- host-тесты async-слоя проходят;
- DSP-тесты не регрессировали;
- время обработки блока остаётся меньше `4.096 ms`;
- Flash и RAM укладываются в бюджет;
- длительный тест на плате не приводит к HardFault или росту счётчиков ошибок.
